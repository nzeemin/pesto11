# Pesto/11: проект компилятора

Документ описывает устройство компилятора Pesto/11 и генерируемого кода. Язык описан отдельно, в [TP3-dialect.md](TP3-dialect.md).

Пометки в документе:
- **[Предложение]** — решение ещё не утверждено;
- **[Позже]** — отложено на следующие этапы.

## 1. Цели и ограничения

- Вход: исходник на диалекте TP3 в кодировке КОИ-8Р.
- Выход: текст на ассемблере MACRO-11.
- Первая цель: УКНЦ под RT-11. Процессор К1801ВМ2, есть EIS (`MUL`, `DIV`, `ASH`, `ASHC`) и FIS (`FADD`, `FSUB`, `FMUL`, `FDIV`).
- Вторая цель **[Позже]**: БК-0010 с ассемблером BKTurbo8. Процессор К1801ВМ1 без EIS и FIS. Всё, что зависит от цели, собрано в одном месте (раздел 10).
- Сборка результата: `macro11` → `.OBJ`, затем `pclink11` → `.SAV`.
- Компилятор на C++17 без внешних зависимостей, в стиле vibasc.

## 2. Командная строка и файлы

```
pesto11 [опции] PROG.PAS
```

На выходе:
- `PROG.MAC` — код программы;
- `PESTO.MAC` — только те процедуры рантайма, которые нужны этой программе.

| Опция | Смысл |
|---|---|
| `-q`, `--quiet` | без лишнего вывода |
| `--onefile` | программа и рантайм в одном `.MAC` |
| `--platform=UKNC` | цель (по умолчанию UKNC; `BK0010` **[Позже]**) |
| `-t`, `--tokenizeonly` | показать лексемы и выйти |
| `-p`, `--parsingonly` | показать модель после парсера и выйти |
| `-v`, `--validationonly` | показать модель после проверки и выйти |
| `-g`, `--showgeneration` | показать сгенерированный код |
| `--noopt` | без peephole-оптимизации; раскладка переходов работает всегда |

Шаблон рантайма `runtime-UKNC.tmac` лежит рядом с исполняемым файлом, как в vibasc.

### 2.1. Кроссплатформенность

Компилятор и `testrunner` собираются и работают на **Windows, Linux и macOS**.

- **Сборка:**
  - `Makefile` для Linux и macOS (GCC и Clang);
  - решение VS2022 для Windows;
  - только C++17 и стандартная библиотека, без системных API, кроме определения пути к исполняемому файлу (`utility.cpp`, по веткам `#ifdef` для каждой ОС, как в vibasc).
- **CI:** GitHub Actions, сборка и тесты на трёх ОС (по образцу `push-matrix.yml` vibasc).
- **Чтение исходников:**
  - файлы открываются в двоичном режиме, байты КОИ-8Р проходят без изменений;
  - концы строк CR/LF, LF и одиночный CR распознаются в любом сочетании (TP3-dialect §1.1);
  - `^Z` — конец файла.
- **Запись `.MAC`:** всегда CR/LF, независимо от ОС. Так файл можно перенести на диск RT-11 и собрать там родным MACRO. Кросс-ассемблер macro11 CR/LF тоже принимает.
- **Пути и имена файлов:**
  - разделители `/` и `\` в `{$I}` принимаются оба;
  - имя include-файла ищется без учёта регистра, в том числе на Linux и macOS, где файловая система различает регистр. Сначала точное совпадение, потом поиск по каталогу без учёта регистра;
  - путь include считается относительно файла, в котором стоит директива;
  - выходные имена `.MAC` — из имени входного файла. Для RT-11 имя файла не длиннее 6 символов; если длиннее, компилятор предупреждает.
- **Внешние инструменты для тестов** (macro11, pclink11, rt11dsk, ukncbtl-debugger) нужны для каждой ОС. `testrunner` ищет их в `x-tools/` с учётом расширения `.exe` на Windows. macro11 и ukncbtl-debugger собираются на всех трёх ОС. Сборку pclink11 и rt11dsk на Linux и macOS **проверить**.
- **Вывод на консоль:** сообщения компилятора только ASCII. Текст из исходника (строки в КОИ-8Р) в сообщения об ошибках выводится как есть или заменяется на `?`, чтобы не ломать терминал.

## 3. Конвейер

Каждая стадия регистрирует ошибки через `RegisterError()`. Если ошибки есть, компиляция останавливается после стадии.

1. **Tokenizer** (`tokenizer.cpp`). Текст превращается в лексемы. Здесь же:
   - комментарии и директивы, включая `{$I файл}` (стек открытых файлов);
   - склейка строк из `'...'` и `#n` в одну лексему-строку;
   - регистр ключевых слов;
   - позиция каждой лексемы (файл, строка, колонка).

   **Лексемы** (`TokenType`):
   - `Identifier` — до 127 символов; стандартные идентификаторы (`Integer`, `Write`…) тоже идентификаторы, их можно переопределить;
   - `Keyword` — 44 зарезервированных слова (TP3-dialect §1.2), `KeywordIndex`;
   - `Integer` — значение в `int64_t` и признак hex. Hex вне `$0000..$FFFF` и десятичная запись больше 2³¹ — ошибка 56 сразу. Десятичный диапазон Integer (с учётом `-32768`) проверяет валидатор;
   - `Real` — значение в `double`;
   - `String` — склеенные `'...'` и `#n`, байты как есть;
   - `Symbol` — `+ - * / = <> < > <= >= := : ; , . .. ( ) [ ] ^`, `SymbolIndex`. `(.` и `.)` дают `[` и `]`;
   - `EOF` — конец главного файла или `^Z` в нём.

   **Поля лексемы:** тип, ключевое слово или знак, исходный текст, значения (`ivalue`, `ishex`, `dvalue`, `svalue`), позиция, маска директив `A B C I R U V X` и признак `separated` — был ли перед лексемой пробел, конец строки или комментарий. По признаку `separated` парсер склеивает `'A'^G` только без промежутка.

   **Ошибки токенизатора:** 55 (строка не закрыта), 56 (целое), 57 (вещественное), 58 (недопустимый символ), 90 (include не найден), 91 (конец файла внутри комментария), 93 (директива), а также «идентификатор длиннее 127 символов» и «вложенный include».

   **Вывод `-t`:** одна лексема на строку — `строка,колонка ТИП значение`. Для include-файла перед позицией стоит имя файла. Когда меняется маска директив, выводится строка `DIRECTIVES` с полным состоянием. Байты строк вне 32..126 печатаются как `#nnn`.

   **`^` — отдельная лексема**, а символ сразу после неё токенизатор **не читает**. Различить управляющий символ `^G`, тип-указатель `^Integer` и разыменование `p^` можно только по месту в грамматике (TP3-dialect §1.5). Поэтому:
   - токенизатор ленивый: лексемы выдаются по одной, по запросу парсера, а не заранее вектором;
   - парсер, увидев `^` там, где ожидается константа, множитель или продолжение строки, вызывает `Tokenizer::ReadControlChar()`. Метод берёт следующий сырой символ, превращает его в управляющий и продолжает обычную токенизацию;
   - **парсер не должен заглядывать за `^` дальше одной лексемы**, пока не решит, что она значит. Иначе символ после `^` уже станет лексемой (`G` — идентификатором);
   - склейку `'A'#13` + `^G` + `'B'` в одну строку делает парсер при разборе строкового литерала.
2. **Parser** (`parser.cpp`). Рекурсивный спуск. Лексемы превращаются в модель программы: описания, типы, тела подпрограмм, деревья выражений.
   - Парсер чисто синтаксический. Например, `X(Y)` разбирается как обобщённый вызов, а приведение это типа, вызов функции или процедуры, решает валидатор.
   - Заглядывание вперёд — не больше одной лексемы (см. `^` выше).
   - **Директивы** (`{$R+}`, `{$I-}`, `{$V-}` …) в поток лексем не попадают. Токенизатор сам ведёт текущее состояние директив и записывает его в каждую лексему (битовая маска). Парсер копирует маску первой лексемы оператора или выражения в узел модели. Так `$R+` и `$I-` действуют с того места, где стоят, и грамматике не нужно знать, что директива может стоять между любыми лексемами.
   - Директивы, действующие на всю программу (`$B`, `$C`), учитываются, только если стоят до первого описания. Иначе выдаётся предупреждение.
   - **Восстановление после ошибки:** парсер пропускает лексемы до `;`, `end` или начала следующего описания и продолжает разбор, чтобы найти и другие ошибки (§11).
   - **Структурные константы** (`(1,2,3)`, `(X:1; Y:2)`, `['a'..'z']`) парсер выдаёт как общее дерево. С типом его сопоставляет валидатор.
   - **Параметры с форматом** (`x:5:2`) парсер принимает у любого вызова. Где формат недопустим, это ошибка валидатора.
3. **Validator** (`validator.cpp`).
   - Таблица символов с вложенными областями видимости.
   - Построение типов, вычисление констант (границы массивов, длины строк, метки `case`).
   - Проверка типов, расстановка неявных преобразований (Integer→Real, Char→String, массив Char→String).
   - Свёртка константных выражений.
   - Раскладка памяти: размеры, смещения полей, смещения локальных переменных и параметров.
   - Проверки `goto` и меток, `forward`.

   Подробно — §4.10.
4. **Generator** (`generator*.cpp`). Обходит модель и для каждой подпрограммы строит список команд. Собирает множество нужных процедур рантайма.
5. **Peephole и раскладка переходов** (`optimizer.cpp`, `branches.cpp`). Микрооптимизации по шаблонам, затем замена недостижимых коротких переходов длинными формами. Всё в памяти, до записи `.MAC` (раздел 9).
6. **Output.** Записывает `.MAC` с выравниванием табуляцией, как в vibasc.
7. **RuntimeGenerator** (`runtime.cpp`). Берёт из шаблона `.tmac` нужные блоки и все их зависимости.

Общие объявления лежат в `main.h`, глобальное состояние — в `main.cpp`. Диспетчеризация по ключевым словам и операциям через статические таблицы `{ключ, &Class::Method}`.

## 4. Модель данных компилятора

Все объявления лежат в `main.h`, функции моделей — в `model.cpp`.

### 4.1. Общие принципы

- **Значения, а не указатели.** Модели хранятся по значению в `std::vector`. Ссылки между ними — целые индексы, `-1` означает «нет». Владельцев и `new`/`delete` нет, модель можно целиком вывести и сравнить в тестах.
- **Общие таблицы программы** лежат в одном объекте `ProgramModel g_program`:
  - типы `types`;
  - подпрограммы `procedures`;
  - символы `symbols`;
  - области видимости `scopes`.
- **Парсер чисто синтаксический.** Он заполняет то, что видно в тексте: имена, структуру, выражения. Ничего не ищет по имени.
- **Валидатор дописывает поля** в те же модели: найденные символы, типы узлов, вычисленные константы, размеры и смещения. В описании ниже такие поля помечены *(В)*.
- **У каждой модели есть `SourcePos pos`** для сообщений об ошибках. У оператора и узла выражения ещё есть маска директив (`$R`, `$I`, `$V`…) из первой лексемы.

### 4.2. Программа

```
ProgramModel
    name, pos                   имя из заголовка program (может не быть)
    types:      vector<TypeModel>
    procedures: vector<ProcedureModel>   [0] — главная программа
    symbols:    vector<SymbolModel>      (В)
    scopes:     vector<ScopeModel>       (В) [0] — стандартные идентификаторы, [1] — программа
```

Главная программа — это `ProcedureModel` с видом `ProcKindProgram` и уровнем 0. Тогда разбор и проверка блока у программы и у подпрограмм одинаковые.

### 4.3. Подпрограмма и блок

```
ProcedureModel
    kind            ProcKindProgram | ProcKindProcedure | ProcKindFunction
    name, pos
    parent          индекс объемлющей подпрограммы (-1 у программы)
    level           0 — программа, 1 — верхний уровень, 2+ — вложенные
    params:         vector<ParamGroupModel>
    resulttype      Token: имя типа результата функции (пусто у тела forward-функции)
    directive       ProcDirNone | ProcDirForward | ProcDirExternal | ProcDirOverlay
    external        ExpressionModel: адрес для external
    block           BlockModel (пустой у forward/external)
    (В) symbol, scope, forwardof (индекс forward-объявления), resulttypeindex,
        paramsize, localsize, asmlabel ("P00012")

ParamGroupModel                 одна группа "var A, B: T"
    isvar
    names:      vector<Token>
    typename    Token, пусто — нетипизированный var-параметр

BlockModel
    declarations: vector<DeclarationModel>   в порядке исходника
    body:         StatementModel             составной оператор begin..end
```

### 4.4. Описания

Разделы `label`/`const`/`type`/`var` и подпрограммы могут идти в любом порядке и повторяться. Поэтому блок хранит **один список описаний в порядке текста**, а не отдельные списки по видам. Валидатор проходит его по порядку: всё, на что ссылаются, должно быть описано раньше.

```
DeclarationModel
    kind            DeclLabel | DeclConst | DeclTypedConst | DeclType | DeclVar | DeclProcedure
    pos
    names: vector<Token>    метки; одно имя у const/type; список имён у var
    type            индекс TypeModel (type, var, типизированная константа)
    value           ExpressionModel — значение const
    initvalue       StructConstModel — значение типизированной константы
    absolute        ExpressionModel — адрес или имя переменной после absolute
    procindex       индекс ProcedureModel для DeclProcedure
    (В) symbols: vector<int>
```

**Значение типизированной константы** — дерево, потому что массив, запись и множество вкладываются друг в друга:

```
StructConstModel
    kind            ConstSimple | ConstList | ConstSet
    pos
    value           ExpressionModel — для ConstSimple
    items: vector<StructConstModel>   для ConstList: элементы массива или поля записи
    fieldname       Token — у элемента записи, `(X: 1; Y: 2)`
    rangeto         ExpressionModel — для элемента множества `'a'..'z'`
```

Массив от записи парсер отличает по `имя :` после скобки. С типом дерево сопоставляет валидатор.

### 4.5. Типы

Тип в тексте и тип после проверки — одна и та же запись `TypeModel` в общем векторе `g_program.types`. Парсер создаёт записи по тексту, валидатор дописывает размеры и разрешает имена.

```
TypeModel
    kind            TypeKindName      — ссылка по имени, пока не разрешена: Integer, MyRec
                    TypeKindEnum, TypeKindSubrange, TypeKindString, TypeKindArray,
                    TypeKindRecord, TypeKindSet, TypeKindPointer, TypeKindFile
                    стандартные (создаёт валидатор): TypeKindInteger, TypeKindByte,
                    TypeKindBoolean, TypeKindChar, TypeKindReal, TypeKindText, TypeKindUntypedFile
    pos
    name            Token: имя для TypeKindName и для ^Name
    ispacked
    enumnames: vector<Token>          перечисление
    lowexpr, highexpr: ExpressionModel поддиапазон; длина строки — в highexpr
    indextype       индекс типа индекса (массив)
    elemtype        элемент массива, база множества, компонент файла, цель указателя
    record          RecordPartModel
    (В) resolved    для TypeKindName — индекс настоящего типа
    (В) low, high   границы поддиапазона и перечисления, длина строки
    (В) size, align размер в байтах и выравнивание (1 или 2)
```

- **`array[A, B] of T` парсер сразу разворачивает** в `array[A] of array[B] of T`, как в TP3 §10.2. Дальше по коду многомерных массивов нет.
- **`^Name` с ещё не описанным типом.** Цель указателя хранится как `TypeKindName`. Валидатор разрешает её в конце раздела `type`, это правило «опережающей ссылки» для указателей.
- **Запись** — фиксированная часть и, возможно, вариантная. Вариант сам может содержать вариантную часть, поэтому структура рекурсивная:

```
RecordPartModel
    fields: vector<FieldModel>        фиксированная часть
    hasvariant
    tagname         Token, пусто — свободное объединение
    tagtype         индекс типа тега
    variants: vector<VariantModel>

FieldModel
    name, pos
    type            индекс TypeModel
    (В) offset

VariantModel
    labels: vector<CaseLabelModel>
    part            RecordPartModel
```

### 4.6. Операторы

Один класс `StatementModel` с видом и полями. У каждого вида используются только свои поля:

```
StatementModel
    kind            StmtEmpty, StmtCompound, StmtAssign, StmtCall, StmtGoto, StmtInline,
                    StmtIf, StmtCase, StmtWhile, StmtRepeat, StmtFor, StmtWith
    pos, directives
    label           Token: метка перед оператором (`10:`), пусто — нет
    target          ExpressionModel: левая часть присваивания; вызов процедуры;
                    переменная цикла for
    expr            ExpressionModel: правая часть; условие if/while/until; селектор case;
                    начальное значение for
    expr2           ExpressionModel: конечное значение for
    downto          for ... downto
    statements: vector<StatementModel>
                    Compound, Repeat — тело по порядку
                    If — [0] then, [1] else (если есть)
                    While, For, With — [0] тело
                    Case — операторы ветки else
    caseelements: vector<CaseElementModel>
    withvars: vector<ExpressionModel>
    gotolabel       Token
    inlineitems: vector<InlineItemModel>
    (В) labelindex, forvar (символ переменной цикла), forlimitslot (ячейка конечного значения),
        withslots (ячейки адресов записей)

CaseElementModel
    labels: vector<CaseLabelModel>
    statement: vector<StatementModel>   ровно один элемент

CaseLabelModel                  также метки вариантов записи
    from            ExpressionModel
    to              ExpressionModel, пустое — одна метка, не диапазон

InlineItemModel                 один элемент между '/'
    sizeprefix      0 | '<' | '>'
    terms: vector<InlineTermModel>   { sign, kind: число | имя | '*', value, name }
```

Ветка `case` хранит оператор в векторе из одного элемента: класс ещё не определён полностью, когда объявляется `CaseElementModel`, а вектор неполного типа C++17 разрешает.

### 4.7. Выражения

Как в vibasc: у выражения свой массив узлов, связи — индексы в этом массиве.

```
ExpressionModel
    nodes: vector<ExpressionNode>
    root            индекс корня, -1 — пустое выражение

ExpressionNode
    kind            NodeInteger, NodeReal, NodeString, NodeNil,
                    NodeIdent          имя: переменная, константа, функция без скобок,
                                       поле внутри with — решает валидатор
                    NodeCall           имя(аргументы): вызов функции, процедуры или приведение типа
                    NodeIndex          base[i, j]
                    NodeField          base.name
                    NodeDeref          base^
                    NodeUnary          op: '+', '-', not
                    NodeBinary         op: + - * / div mod and or xor shl shr = <> < > <= >= in
                    NodeSet            [a, b..c]
    pos, directives
    token           лексема: имя, литерал или операция
    left, right     индексы операндов; у Index/Field/Deref left — база
    args: vector<ArgModel>          Call, Index: { node, width, decimals }
                                    width/decimals — формат Write(x:5:2), -1 — нет
    setitems: vector<SetItemModel>  { from, to } — индексы узлов, to = -1 — не диапазон
    (В) type        индекс TypeModel результата
    (В) symbol      найденный символ для Ident/Call/Field
    (В) isconst, constvalue        { ivalue, dvalue, svalue, setbits[32] }
    (В) convert     неявное преобразование результата: нет, Integer→Real, Char→String,
                    массив Char→String
```

- **Строковый литерал** — это уже склеенный `'A'#13^G'B'`: парсер собирает части и `^X` (TP3-dialect §1.5) в один `NodeString`.
- **Приоритеты операций** парсер разбирает рекурсивным спуском по грамматике (TP3-dialect §2.6), поэтому узлам не нужен признак скобок: дерево уже учитывает порядок.
- **Константные выражения** в `const`, в границах типов и в метках `case` — это обычные `ExpressionModel`. По грамматике TP3 там только знак и литерал или имя, но модель позволяет больше, если решим расширить язык.

### 4.8. Символы и области видимости (заполняет валидатор)

```
SymbolModel
    name            исходное написание; поиск без учёта регистра
    pos
    kind            SymConst, SymTypedConst, SymType, SymVar, SymParam, SymVarParam,
                    SymProcedure, SymFunction, SymLabel, SymEnumValue,
                    SymStdProc, SymStdFunc     стандартные Write, Length, …
    type            индекс TypeModel
    scope, level
    constvalue      для констант и значений перечисления
    procindex       для подпрограмм
    stdindex        номер стандартной подпрограммы
    offset          смещение в кадре (локальные, параметры)
    asmlabel        метка для глобальных ("V00003")
    absolute        символ или адрес, если переменная absolute

ScopeModel
    parent          объемлющая область
    procindex       подпрограмма-владелец

```

- Поля записей — не символы: они лежат в `FieldModel` своего типа. Внутри `with` валидатор ищет имя сначала в полях открытых записей, потом в областях видимости.
- Стандартные идентификаторы лежат в области `[0]`. Пользователь может их переопределить: поиск идёт от внутренней области к внешней.

### 4.9. Вывод `-p`

Описания и операторы печатаются по строке с отступом в два пробела. Типы и выражения пишутся одной строкой; каждая бинарная и унарная операция берётся в скобки, так что порядок вычисления виден сразу:

```
PROGRAM Hello
  VAR Count, X: Integer
  PROCEDURE Show(A: Integer; var S: Str)
    BEGIN
      CALL WriteLn(A:5, S)
  BEGIN
    ASSIGN Count := ((Count + 1) * 2)
    IF (Count > 10) {$R+}
      THEN
        CALL Show(Count, 'Big'#13#10)
    ASSIGN X := (not (-Count)) {$defaults}
```

- Строки печатаются так же, как в `-t`: склеенные части `'...'`, а байты вне 32..126 — как `#nnn` (`^G` выглядит как `#7`).
- Состояние директив выводится только у оператора, где оно изменилось: `{$R+,I-}` — отличия от значений по умолчанию, `{$defaults}` — возврат к ним.
- Вывод `-v` будет тем же форматом плюс поля, помеченные *(В)*.

### 4.10. Валидатор

Валидатор (`validator.cpp`) проверяет программу по семантике TP3 (TP3-dialect §3–§7) и дописывает в модель поля *(В)*: символы, типы, константы, размеры, смещения. После него генератору не нужно ничего искать по имени и проверять: модель полная и корректная. Правила языка здесь не повторяются, а только как и в каком порядке валидатор их проверяет.

**Порядок работы**

1. **Стандартная область `[0]`.** Валидатор создаёт стандартные типы, константы, переменные и подпрограммы из TP3-dialect §7:
   - типы: `Integer`, `Byte` (поддиапазон 0..255), `Boolean` (перечисление `False`, `True`), `Char`, `Real`, `Text`;
   - константы `True`, `False`, `MaxInt`, `Pi`;
   - переменные: стандартные файлы, `Mem`, `HeapPtr`, `BufLen`;
   - стандартные процедуры и функции.

   Всё берётся из одной таблицы `{имя, вид, номер, &Validator::Method}`. Идентификаторы со статусом «нет» в таблице тоже есть, но помечены: их использование даёт ошибку 200 «Not supported in Pesto/11», а не «неизвестный идентификатор».
2. **Область программы `[1]`** и обход блоков, начиная с блока программы. В каждом блоке:
   1. описания — **по порядку текста**, каждое сразу заносится в область видимости. Поэтому ссылка на ещё не описанное имя — ошибка, как в TP3;
   2. после всех описаний — проверки, которые можно сделать только в конце: у каждой `forward`-подпрограммы есть тело (73), опережающие указатели разрешены (42);
   3. тело блока: операторы и выражения;
   4. раскладка памяти блока: смещения локальных переменных и параметров, временные ячейки.

   Вложенные подпрограммы обрабатываются там, где встретились в списке описаний: своя область видимости, затем тот же порядок шагов.

**Описания**

- **`label`** — символ метки. Валидатор отмечает, где метка поставлена и где на неё переходят. В конце блока: каждая метка из `goto` должна быть поставлена в этом же блоке (40, 72).
- **`const`** — значение вычисляется сразу (свёртка констант), получается `SymConst` с типом и значением:
  - число со знаком;
  - строка: длина 1 даёт тип Char, иначе String;
  - имя другой константы.

  Здесь же проверяется диапазон целого: `32768` допустимо только под унарным минусом (56).
- **`type`** — разрешение записи `TypeModel`:
  - `TypeKindName` → `resolved` по символу типа (36, если имя — не тип);
  - **перечисление** — значения становятся символами `SymEnumValue` в текущей области;
  - **поддиапазон:** границы — константы одного порядкового типа, не Real (51), нижняя не больше верхней (52);
  - **`string[n]`:** n в 1..255 (49);
  - **массив:** тип индекса порядковый, не Real;
  - **множество:** база не больше 256 значений в 0..255 (70);
  - **файл:** компонент не файл (68);
  - **запись:** имена полей не повторяются (43); метки вариантов совпадают по типу с тегом;
  - **указатель на ещё не описанный тип** откладывается до конца раздела `type`;
  - размер и выравнивание — по DESIGN §6.2, смещения полей — с выравниванием слов.
- **Типизированная константа** — тип, затем дерево `StructConstModel` сопоставляется с ним: число элементов массива, поля записи по порядку, элементы множества, массив Char как строка той же длины.
- **`var`** — символ `SymVar` на каждое имя. У `absolute` проверяются правила 75: адрес — целая константа или переменная.
- **Подпрограмма:**
  - символ `SymProcedure` или `SymFunction` в текущей области;
  - если в той же области уже есть `forward`-подпрограмма с этим именем, это её тело: параметры и тип результата берутся из `forward`-объявления, а у тела их быть не должно;
  - типы параметров — только имена типов. Файл — только `var`-параметр (67);
  - тип результата — скаляр, Real, строка или указатель (48);
  - `overlay` — ошибка 200;
  - `external` — адрес вычисляется как целая константа.

**Выражения**

Проход снизу вверх по дереву узлов. Каждый узел получает `type`, а константный — ещё `isconst` и `constvalue`.

- **Имя** ищется так:
  - сначала в полях записей открытых `with`, от внутреннего к внешнему;
  - потом по областям видимости от текущей к `[0]`.

  Найденный символ определяет вид узла: переменная, константа (подставляется значение), вызов функции без аргументов, значение перечисления.
- **Имя функции внутри её же тела** слева от `:=` — это переменная результата. В выражении — рекурсивный вызов.
- **`Call`** — по символу:
  - вызов пользовательской подпрограммы: число и типы аргументов, `var`-аргумент — переменная того же типа (44); для строк длина проверяется при `$V+`;
  - **стандартная подпрограмма** — через свой метод в таблице, потому что у многих особый синтаксис: `Write` с форматами, `Read` с переменными, `New`, `SizeOf(тип)`, `Addr`, `Concat` с любым числом аргументов, `Succ`/`Pred`/`Ord`/`Chr`;
  - **приведение типа**, если имя — тип: `Char(78)`, `Day(3)`.
- **Операции** — по таблице TP3-dialect §4:
  - тип результата;
  - неявные преобразования: Integer→Real, Char→String, массив Char→String, смешение Byte и Integer. Они записываются в узел, генератор их выполняет;
  - ошибки 44 и 47 при неподходящих типах.
- **Свёртка констант:**
  - целые — в 16 битах с переполнением, как при выполнении в TP3;
  - Real — в `double`, с переводом в DEC F при генерации;
  - строки и множества тоже сворачиваются;
  - деление на константный ноль не сворачивается: это будет ошибка выполнения 02.
- **Без каскада ошибок.** Узел с ошибкой получает тип «ошибка». Проверки над таким операндом молчат, поэтому одна ошибка не порождает цепочку следующих.

**Операторы**

- **Присваивание:** левая часть — переменная, типизированная константа или имя текущей функции, но не файл (54). Тип правой части совместим с левой (44). Real := Integer допустимо.
- **`if`, `while`, `until`:** условие Boolean (20).
- **`for`:** переменная — простая переменная порядкового типа, не Real. Начальное и конечное значения того же типа.
- **`case`:**
  - селектор порядковый, не Real;
  - метки — константы того же типа (46), без повторов;
  - `else` — список операторов.
- **`with`:** каждая переменная — запись (29); её поля открываются для вложенного оператора.
- **`goto`:** метка описана в этом блоке (40, 72); переход внутрь `for` снаружи запрещён (71).
- **Формат `:w:d`** допустим только у `Write`, `WriteLn` и `Str`. Ширина и точность — Integer; точность — только для Real.

**Раскладка памяти** (по DESIGN §6 и §7.3)

- **Глобальные переменные и типизированные константы** получают ассемблерные метки `V00001`, `C00001`.
- **Параметры:** положительные смещения от R5 с учётом места под Real-результат и скрытого адреса строкового результата.
- **Локальные переменные:** отрицательные смещения. У вложенных подпрограмм `-2(R5)` занимает статическая ссылка.
- **Временные ячейки**, которые нужны операторам, выделяет тоже валидатор: конечное значение `for`, адреса записей `with`. Так генератор получает готовый размер кадра. Буферы строк и множеств для промежуточных результатов выражений в кадре не нужны: они живут на стеке (§7.6).
- Размер блока файла (FIB) пока условный — 528 байт; окончательный формат — DESIGN §6.4.

**Ошибки**

- Коды TP3 (TP3-dialect §11.1) и формат `FILE.PAS(12,5): error 44: Type mismatch`.
- Неподдерживаемые в Pesto/11 конструкции — ошибка 200.
- После ошибки валидатор продолжает проверку следующего оператора и описания.

**Вывод `-v`**

Формат `-p` (§4.9) плюс результаты проверки:
- у `CONST` — вычисленное значение и тип;
- у `TYPE` и `VAR` — размер, а у переменных — смещение (`-4(R5)`) или метка (`V00003`);
- у подпрограмм — размеры параметров и кадра;
- у выражений — тип корня, свёрнутые константы как значения и неявные преобразования явным вызовом: `ToReal(I)`, `ToString(C)`.

Точный формат закрепят тесты валидатора.

### 4.11. Генератор

Генератор получает модель, которую проверил и разметил валидатор, и выдаёт текст MACRO-11. Новых проверок языка в нём нет: всё, что не так с программой, уже нашёл валидатор. Если генератор встречает конструкцию, которую ещё не умеет генерировать, он пишет в код строку с `TODO`, и тест на эту конструкцию падает (§12). Шаблоны кода для конструкций языка — в разделе 7, здесь устройство самого генератора.

**Файлы**

| Файл | Что |
|---|---|
| `generator.cpp` | класс `Generator`: обход программы, подпрограммы, пролог и эпилог, данные, сборка выходного файла |
| `generator-stmt.cpp` | операторы (§7.4) |
| `generator-expr.cpp` | выражения, условия-переходы, адресация переменных (§7.2, §7.5) |
| `generator-std.cpp` | вызовы стандартных подпрограмм: таблица `{номер StdRoutine, &Generator::Method}` (§7.7) |
| `optimizer.cpp`, `branches.cpp` | peephole и раскладка переходов (§9) |
| `runtime.cpp` | отбор блоков из `runtime-UKNC.tmac` (§8) |

**Модель вывода**

```
CodeLine
    label           метка строки, пусто — нет
    opcode          мнемоника или директива: MOV, BEQ, .WORD, .BLKB
    operands        текст операндов: "#12., -4(R5)"
    comment         комментарий
    words           размер в словах (§9.2): считается по opcode и режимам адресации
    kind            обычная команда | переход (Bxx, BR, SOB) | метка | данные | комментарий-строка
    target          для перехода: метка цели
    flags           R0 живой после команды (для peephole, §9.1)

ProcedureCode
    procindex
    lines: vector<CodeLine>

FinalModel
    procedures: vector<ProcedureCode>   главная программа первой
    data: vector<CodeLine>              константы, типизированные константы, глобальные переменные
    runtimeneeds: set<RuntimeSymbol>
```

Команды добавляются вызовами вида `Emit("MOV", src, dst, comment)`. Строки собираются **по подпрограммам**: peephole и раскладка переходов работают внутри одной подпрограммы, и переход за её границы не бывает (TP3 запрещает `goto` из блока).

**Операнды**

Генератор работает не со строками, а с описанием операнда, и превращает его в текст только при выводе:

```
Operand
    mode        регистр | (Rn) | (Rn)+ | -(Rn) | n(Rn) | @n(Rn) | #n | метка | @#n
    reg, value, label
```

Из описания сразу видно, сколько слов займёт команда, и peephole может сравнивать операнды без разбора текста. Переменная превращается в операнд через `GetVariableOperand(expr, node)`:
- глобальная переменная — метка `V00003`, со смещением поля: `V00003+4`;
- локальная переменная или параметр — `-4(R5)`, `6(R5)`;
- `var`-параметр — `@6(R5)`;
- переменная объемлющей подпрограммы — статическая ссылка в R3 (§7.3), затем `-6(R3)`;
- поле внутри `with` — адрес записи из ячейки `with` в R3, затем `n(R3)`;
- элемент массива, разыменование указателя, поле по указателю — адрес вычисляется в R3, операнд `(R3)` или `n(R3)` (§7.5).

Если переменную можно адресовать без кода (первые четыре случая), команда работает прямо с ней, иначе сначала выполняется подготовка адреса.

**Порядок обхода**

1. Главная программа: `START:`, блок `INIT` рантайма, тело, блок `TERM`.
2. Все подпрограммы по порядку их описания в тексте, вложенные — сразу после объемлющей. Каждая: метка `Pnnnnn:`, пролог, тело, эпилог (§7.3). У `forward` код выдаётся по телу, у `external` кода нет: вызов идёт на адрес.
3. Данные: строковые константы (`Knnnnn`, одинаковые — один раз), типизированные константы (`Cnnnnn` с начальными значениями), глобальные переменные и временные ячейки главной программы (`Vnnnnn`, `.BLKW`/`.BLKB` с `.EVEN`).
4. Метка конца программы `PEND::` — начало кучи (§6.1). Рантайм линкуется после программы, поэтому при отдельном `PESTO.MAC` метка стоит в конце этого файла, иначе — в конце `PROG.MAC`.

**Выходной файл `PROG.MAC`**

```
        .TITLE  PROG
        .MCALL  .EXIT, .SETTOP          ; что нужно INIT/TERM
        .GLOBL  WRSTRI, WRINT, ...      ; используемые блоки рантайма (не в Turbo8)
; program Hello;                         ; исходные строки — комментариями
START:: ...
P00001: ...
K00001: .BYTE   5., 'H, 'e, 'l, 'l, 'o
        .EVEN
V00001: .BLKW   1                       ; I: Integer
PEND::
        .END    START
```

Перед кодом каждого оператора — строка исходника комментарием, как в vibasc и OMSI. Так листинг `.LST` легко читать и искать место ошибки выполнения.

**Выражения**

- **Значение в R0** (§7.2). Генератор сначала смотрит, нельзя ли взять операнд прямо: константа, переменная с готовым операндом. Если нельзя — вычисляет в R0, левый операнд при этом сохраняется на стеке.
- **Свёрнутые валидатором константы** выводятся как `#n.` — дерево под ними не обходится.
- **Неявные преобразования** из `convert` узла: `ToReal` — вызов `ITOF` (Integer со стека → Real на стеке); `ToString` из Char — строка длины 1 во временном буфере.
- **Real** — всегда на стеке, 2 слова, операции FIS (§7.2).
- **Строки и множества** — во временных буферах на стеке (§7.6), в R0 адрес буфера.
- **Условия** (`if`, `while`, `until`, `for`) генерируются функцией `GenerateCondition(expr, label, jumpiftrue)`, которая не вычисляет значение, а переходит:
  - сравнение — `CMP`/`CMPB` и знаковый или беззнаковый `Bxx`;
  - Boolean-переменная — `TSTB` и `BEQ`/`BNE`;
  - `not` — тот же переход с обратным условием;
  - `and`/`or` — цепочка переходов, если в операндах нет вызовов функций (результат тот же при любом порядке вычисления). Если вызовы есть, оба операнда вычисляются в значения и объединяются `BIC`/`BIS`, пока не решён вопрос о полном вычислении (TP3-dialect §13).

**Подпрограммы и вызовы** — по §7.3: место под Real-результат, адрес строкового результата, параметры слева направо, статическая ссылка в R4, `CALL`. Генератор берёт смещения и размеры из модели (*(В)*-поля валидатора), сам ничего не раскладывает. Исключение — временные буферы выражений: они на стеке и в размер кадра не входят.

**Стандартные подпрограммы** — у каждой метод генерации в таблице `generator-std.cpp`. Большинство — вызов блока рантайма с аргументами в регистрах или на стеке; соглашение каждого блока описано в его комментарии в `.tmac`. Часть разворачивается на месте: `Ord`, `Chr`, `Succ`, `Pred`, `Odd`, `Hi`, `Lo`, `Swap`, `Mem[]`, `Abs` для Integer.

**Проверки времени выполнения**

- `{$R+}` у оператора — проверка индексов и присваиваний в поддиапазон: `CALL RNGCHK` с границами словами после вызова.
- `{$I+}` — после каждой операции ввода-вывода `CALL IOCHK`: если операция установила ошибку, программа останавливается. При `{$I-}` проверки нет, код ошибки читает `IOresult`.
- Деление на ноль в `div`/`mod`: после `DIV` — `BVC .+6` / `CALL DIVZER` (ошибка 02). Тот же флаг V ловит переполнение `-32768 div -1`.

**Рантайм.** Каждый вызов блока рантайма добавляет его символ в `runtimeneeds`. После генерации `runtime.cpp` выбирает блоки с зависимостями `;## Need` и пишет `PESTO.MAC` (или дописывает в тот же файл при `--onefile`).

**Порядок реализации** (каждый шаг — с тестами-эталонами `.MAC`, сборкой macro11 и pclink11):
1. Каркас: `START`, `INIT`/`TERM`, данные, `Write`/`WriteLn` строковых констант и Integer — первая программа «Hello world» на УКНЦ.
2. Integer и Boolean: выражения, присваивание, условия-переходы, `if`, `while`, `repeat`, `for`, `case`, `goto`, `$R+`.
3. Подпрограммы: кадр, параметры, функции, рекурсия, вложенность, статическая цепочка, `forward`, `external`, `Exit`, `Halt`.
4. Массивы, записи, указатели, `with`, `Mem`, `absolute`, типизированные константы, куча.
5. Строки.
6. Множества.
7. Real.
8. `Read`/`ReadLn`, экран и клавиатура.
9. Файлы.
10. Peephole и раскладка переходов (раскладка нужна уже с шага 2: до неё все условные переходы генерируются длинной формой).

## 5. Имена в ассемблере

**Значимы только первые 6 символов имени** (RAD50). Поэтому идентификаторы Pascal в ассемблер не попадают, все имена генерируются. В комментарии пишется исходное имя.

| Что | Метка | Пример |
|---|---|---|
| процедура или функция | `P` + номер | `P00012:` ; `procedure DrawBox` |
| глобальная переменная | `V` + номер | `V00003:` ; `var Count: Integer` |
| типизированная константа | `C` + номер | `C00001:` |
| строковая или структурная константа в коде | `K` + номер | `K00007:` |
| внутренняя метка (переходы) | `L` + номер | `L00123:` |
| метка `goto` | `G` + номер | `G00004:` |
| процедура рантайма | имя блока `.tmac` | `WRINT`, `STCP`, `FADD` |

- Номер — пятизначный десятичный счётчик: `P00001`..`P99999`.
- Имена рантайма не начинаются с `P`, `V`, `C`, `K`, `L`, `G` с цифрой следом, поэтому не пересекаются с генерируемыми.
- Локальные метки `nn$` используются только внутри блоков рантайма.

## 6. Память и данные

### 6.1. Раскладка памяти программы (RT-11, УКНЦ)

```
000000  векторы прерываний, системная область RT-11
...     стек RT-11 при запуске (ниже 001000)
001000  START: код программы
        код подпрограмм
        рантайм (PESTO.MAC)
        константы, типизированные константы
        глобальные переменные
HEAPLO: начало кучи                         ↓ куча растёт вверх
        ...свободная память...
        стек программы                       ↑ стек растёт вниз
TOP:    верх доступной памяти (.SETTOP)
```

- В INIT программа запрашивает верх памяти и переносит туда SP. Стека RT-11 ниже 1000 мало для рекурсии и строковых временных значений:
  ```
          MOV     SP, INIT$S      ; стек RT-11, его восстанавливает TERM
          MOV     #-2, R0         ; .SETTOP: просим всю память
          EMT     354             ; в R0 — реальный верх
          BIC     #1, R0          ; SP всегда чётный
          MOV     R0, SP
  ```
- `HeapPtr` (`HEAPPT`) в начале равен `PEND` (`HEAPLO` на схеме), `FREELS` = 0. Обе переменные заданы статически в блоке рантайма `HEAPPT` (`.WORD PEND`, `.WORD 0`), поэтому INIT их не трогает, а блок попадает в программу только вместе с кучей.
- **Столкновение кучи и стека** даёт ошибку выполнения FF. Пока проверяется только в `New`/`GetMem`: ошибка, если `HeapPtr + размер + HEAPRS > SP`. `HEAPRS` = 256 байт — запас для стека под кадры и временные значения рантайма. Проверка в прологе подпрограмм отложена (§14).

**Куча.** Блоки выделяются по словам: размер округляется вверх до чётного, минимум 4 байта, чтобы свободный блок вместил свой заголовок. У занятого блока заголовка нет: размер при `Dispose`/`FreeMem` известен из типа указателя или из аргумента, как в TP3.

Свободный блок хранит заголовок в себе:
```
+0  адрес следующего свободного блока (0 — конец списка)
+2  размер блока в байтах
```
- `New`/`GetMem`: первый подходящий блок из списка `FREELS`. Если остаток ≥ 4 байт, он остаётся в списке на месте блока, иначе блок отдаётся целиком. Не нашли — берём от `HeapPtr` с проверкой столкновения.
- `Dispose`/`FreeMem`: если блок кончается на `HeapPtr`, `HeapPtr` опускается до начала блока. Иначе блок добавляется в начало списка. Соседние свободные блоки не сливаются (можно добавить позже).
- `Mark(p)`: `p := HeapPtr`. `Release(p)`: `HeapPtr := p`, список свободных очищается. Смешивать `Dispose` с `Mark`/`Release` по TP3 нельзя (результат не определён), поэтому такой `Release` допустим.
- `MemAvail` = `SP − HEAPRS − HeapPtr` плюс размеры всех свободных блоков. `MaxAvail` = наибольшее из `SP − HEAPRS − HeapPtr` и размеров свободных блоков. Оба в байтах, тип Integer: больше 32767 — отрицательное число, как в TP3.
- Значение `nil` = 0; разыменование `nil` не проверяется, как в TP3.
- **[Предложение]** Глобальные переменные не обнуляются, как в TP3. Секцию можно заполнить нулями (`.BLKW`), это бесплатно, но программы не должны на это рассчитывать.

### 6.2. Представление типов

| Тип | Размер | Выравнивание | Формат |
|---|---|---|---|
| Integer | 2 | слово | дополнительный код |
| Byte, Char, Boolean, перечисление и поддиапазон ≤ 256 значений в 0..255 | 1 | байт | беззнаковый байт; Boolean: 0/1 |
| другие перечисления и поддиапазоны | 2 | слово | как Integer |
| Real | 4 | слово | DEC F_floating |
| указатель | 2 | слово | адрес, `nil` = 0 |
| `string[n]` | n+1 | байт | `[0]` длина, дальше символы |
| `set of T` | `(Max div 8)-(Min div 8)+1` | байт | бит `E mod 8` в байте `(E div 8)-(Min div 8)` |
| массив | n × размер элемента | как у элемента | правый индекс меняется быстрее |
| запись | сумма полей с заполнителями | слово, если есть поле-слово | варианты накладываются |
| файл | размер FIB | слово | раздел 6.4 |

**Выравнивание**:
- поле или переменная с выравниванием «слово» получает чётное смещение;
- размер записи или массива с таким выравниванием округляется до чётного;
- все глобальные переменные, локальные переменные и параметры занимают целое число слов, даже однобайтовые;
- после байтовых данных в секции данных ставится `.EVEN`.

### 6.3. Значения во время вычисления

| Вид | Где лежит результат выражения |
|---|---|
| Integer, Byte, Char, Boolean, перечисление, указатель | регистр R0, всегда 16 бит; байтовые значения расширены нулём |
| Real | 2 слова на стеке, порядок слов как требует FIS (как в vibasc) |
| строка | временный буфер (раздел 7.6), в R0 его адрес |
| множество | временный 32-байтовый буфер, в R0 его адрес |
| массив, запись | адрес в R0, значение не копируется |

### 6.4. Файлы

**Обмен с диском в RT-11.** `.READW`/`.WRITW` получают канал, адрес буфера, **число слов** и **номер начального блока**: обмен всегда начинается с начала блока (512 байт), длина — в словах, буфер — по чётному адресу; `.WRITW` дополняет неполный последний блок нулями. Поэтому чтение и запись идут через буфер блока в FIB; прямо в переменную программы — только при выровненном начале, длине, кратной блоку, и чётном адресе.

**Блок файла (FIB)** — содержимое файловой переменной (`Text`, `file of T`, `file`), лежит там же, где переменная: в данных или в кадре. 536 байт: заголовок 24 байта и буфер блока.

| Смещение | Размер | Поле | Назначение |
|---|---|---|---|
| 0 | байт | `FLAGS` | биты 0–2: устройство (0 — файл на диске, 1 — `CON:`, 2 — `TRM:`, 3 — `KBD:`, 4 — `LST:` **[Позже]**); бит 3 — в буфере прочитанный блок; бит 4 — буфер изменён; бит 6 — запись разрешена; бит 7 — чтение разрешено (биты 6–7 как в TP3) |
| 1 | байт | `CHAN` | канал RT-11 1–14, 0 — файл закрыт |
| 2 | 4 слова | `NAME` | имя для `.LOOKUP`/`.ENTER` в RAD50: устройство, имя (2 слова), тип; заполняет `Assign` |
| 10 | слово | `BLOCK` | номер блока файла в буфере |
| 12 | слово | `POS` | позиция текущего байта в буфере, 0–511 |
| 14 | слово | `SIZE` | длина файла в блоках (`.LOOKUP` при `Reset`, `.ENTER` при `Rewrite`) |
| 16 | слово | `RECLEN` | длина записи: компонент типизированного файла, 128 для нетипизированного, 1 для текста |
| 20 | слово | `RECCNT` | число записей (`FileSize`) |
| 22 | слово | `CURREC` | номер текущей записи (`FilePos`) |
| 24 | 512 байт | `BUFFER` | буфер блока |

**Текстовый файл** (как в TP3): строки через CR/LF. Чтение и запись последовательные через буфер. При записи `Close` добавляет ^Z (для RT-11 он необязателен, но так делает TP3), остаток блока — нули. При чтении ^Z — конец файла, нулевые байты пропускаются (так другие программы RT-11 дополняют текстовые файлы). `Eoln`/`Eof`/`SeekEoln`/`SeekEof` смотрят следующий символ в буфере.

**Типизированный файл** (как в TP3, §22.18.2.3.1): первые 4 байта — число записей и длина записи, записи идут подряд. Запись `n` начинается с байта `4 + n · RECLEN`: блок — `div 512`, позиция — `mod 512` (32-битное деление). Запись может пересекать границу блоков, тогда копируется по частям. `Seek` меняет `CURREC`, блок подгружается при обращении. `Close` переписывает заголовок в блоке 0, если число записей изменилось.

**Нетипизированный файл**: записи по 128 байт, как в TP3 (`BlockRead`/`BlockWrite`), без заголовка. Запись `n` — блок `n div 4`, смещение `(n mod 4) · 128`. Выровненные передачи идут прямо в переменную, остальные — через буфер.

**Устройства** `CON:`, `TRM:`, `KBD:` (через `Assign(F, 'CON:')`) используют только `FLAGS`; ввод-вывод — подпрограммами консоли (§7.7). Стандартные `Input`, `Output`, `Con`, `Trm`, `Kbd` — такие же FIB в рантайме, без буфера.

**Имена и каналы.** `Assign(F, 'DEV:NAME.TYP')`: устройство по умолчанию `DK:`, буквы переводятся в прописные, имя — в RAD50. `Reset` — `.LOOKUP`, `Rewrite` — `.ENTER` с размером 0 (место отводит RT-11), `Close` — `.CLOSE`: лишние блоки отрезаются, старый файл с тем же именем заменяется. Без `Close` записанное теряется, как в TP3. Каналы 1–14 выдаются при открытии; свободных нет — I/O-ошибка F3.

**I/O-ошибки.** При `{$I+}` после каждой операции проверяется код (`IOCHK`), при `{$I-}` код сохраняется для `IOresult`. Соответствие: `.LOOKUP` не нашёл файл — 01; файл не открыт для чтения, записи, вообще — 02, 03, 04; `.ENTER` без места — F1; запись за концом отведённого места — F0; `Seek` за конец — 91; неожиданный конец файла — 99. **[P11]** Аппаратная ошибка чтения или записи — F4.

**`Append`** в TP3 3.0 нет (он появился в TP4), а RT-11 не дописывает в существующий файл: файлы непрерывные. **[Позже]**

**USR и верх памяти** (проверено в эмуляторе программой на ассемблере): `.GVAL` 266 даёт адрес USR, бит 001000 слова `CONFIG` (`.GVAL` 300) — USR резидентный.
- `SET USR NOSWAP`: USR в 135316, `.SETTOP #-2` возвращает 135314 — верх памяти программы сам оказывается ниже USR.
- `SET USR SWAP`: USR в 135422, `.SETTOP #-2` возвращает 145420 — память программы перекрывает место USR (2 К слов). Перед `.LOOKUP` 8 КБ под верхом памяти заполнены узором, после `.LOOKUP` узор цел: монитор сохраняет перекрытую область (в SWAP.SYS) и восстанавливает её после работы USR.

В обоих случаях стек и куча программы не портятся, INIT менять не нужно. Цена подкачки — обращения к диску при каждом вызове USR (`.LOOKUP`, `.ENTER`, `.CLOSE`, `.DELETE`, `.RENAME`); `.READW`/`.WRITW` USR не нужен. **[Позже]** Можно избежать подкачки, указав в ячейке 46 место для USR.

## 7. Генерация кода

### 7.1. Регистры

| Регистр | Назначение |
|---|---|
| R0 | аккумулятор: результат выражения и функции |
| R1 | младшая часть пары R0:R1 для `MUL`/`DIV` |
| R2 | правый операнд операции, когда его нельзя взять прямо в команду |
| R3 | адреса: статическая цепочка, позже элементы массивов и указатели |
| R4 | статическая ссылка при вызове вложенной подпрограммы (§7.3); второй адресный регистр |
| R5 | указатель кадра текущей подпрограммы |
| SP (R6) | стек |
| PC (R7) | — |

Это роли по умолчанию, а не жёсткое закрепление. Регистры PDP-11 равноправны, поэтому генератор берёт тот, который в данном месте свободен и даёт меньше команд: например, если два операнда сравнения оба требуют вычисления адреса, второй адрес идёт в R4. Жёстко закреплены только R5 (кадр), SP и пара R0:R1 у `MUL`/`DIV`, которой этого требует сама команда.

- **Через любой вызов (процедуры, функции, рантайма) сохраняются только R5 и SP.** R0–R4 портятся. Кодогенератор не держит значения в регистрах через вызов: промежуточные результаты кладёт в стек.
- Рантайм обязан сохранять R5. **Внимание:** некоторые блоки рантайма vibasc используют R5 как рабочий регистр (например, `FCMP`). При переносе их нужно исправить.
- Каждый блок рантайма в комментарии описывает входные регистры, выход и что портит.

### 7.2. Выражения

Модель «аккумулятор плюс стек». Результат в R0. Если правый операнд сложный, левый сохраняется на стеке.

Простые операнды используются прямо в командах:
- глобальная переменная: `V00003`;
- локальная переменная или параметр-значение: `-4(R5)`, `6(R5)`;
- `var`-параметр: `@6(R5)` — косвенно, адрес в регистр не загружается;
- константа: `#12.`.

**Главный принцип: меньше команд и меньше обращений к памяти.** PDP-11 умеет выполнять операции прямо над памятью, это используется везде, где возможно:

```
        INC     -4(R5)                  ; I := I + 1
        ADD     -4(R5), V00002          ; B := B + I
        ADD     #5., @6(R5)             ; P := P + 5       (P — var-параметр)
        MOV     #-1, -6(R5)             ; X := -1
        CLR     V00003                  ; A := 0
        TST     @6(R5)                  ; if P = 0 ...
        CMP     -4(R5), #10.            ; if I < 10 ...
        MOVB    #'A, V00010             ; C := 'A'
```

Через R0 идут только сложные выражения. Шаблоны peephole (§9.1) собирают оставшиеся случаи вида «загрузить в R0, выполнить операцию, записать».

```
; A := B + C * 3            (все Integer, A,B глобальные, C локальная)
        MOV     -4(R5), R1      ; C
        MUL     #3., R1         ; R1 = младшее слово произведения
        MOV     V00002, R0      ; B
        ADD     R1, R0
        MOV     R0, V00001      ; A :=
```

```
; X := F(Y) - G(Z)          (сложные операнды с обеих сторон)
        ...вызов F, результат в R0
        MOV     R0, -(SP)       ; сохранить левый операнд
        ...вызов G, результат в R0
        MOV     R0, R1
        MOV     (SP)+, R0
        SUB     R1, R0
```

Правила:
- Загрузка байта: `CLR R0` / `BISB x, R0`. Голый `MOVB` в регистр запрещён, он расширяет знак.
- Запись байта: `MOVB R0, x`.
- **Integer `*`**: `MUL src, R1` (нечётный регистр — только младшее слово, переполнение не проверяется, как в TP3).
- **`div`/`mod`**: `MOV a, R1` / `SXT R0` / `DIV b, R0`. Частное в R0, остаток в R1. При делении на ноль процессор ставит флаги V и C: проверка `BVS` даёт ошибку выполнения 02.
- **`shl n`**: `ASH #n, R0`.
- **`shr n`**: `ASH #-n, R0` / `BIC #маска, R0`. Для переменного `n` — подпрограмма рантайма.
- **Real**: операнды кладутся на стек, затем `FADD SP` / `FSUB SP` / `FMUL SP` / `FDIV SP`. Сравнение через `FCMP` рантайма. Integer→Real через `ITOF`.
  - **Константы** компилятор переводит из `double` в DEC F с округлением к ближайшему. Константа вне диапазона DEC F (примерно 2.9E−39..1.7E+38, кроме нуля) — ошибка компиляции «Real constant out of range». Константа кладётся на стек двумя командами `MOV #старшее, -(SP)` после `MOV #младшее, -(SP)`; ноль — `CLR -(SP)` дважды.
  - **Переменная** на стек: `MOV 2+адрес, -(SP)`, затем `MOV адрес, -(SP)` (на вершине старшее слово); со стека в переменную — в обратном порядке.
  - **Ошибки FIS.** INIT ставит свой обработчик на вектор 244 (прерывание FIS), сохранив прежний; TERM возвращает прежний. Переполнение — ошибка выполнения 01, деление на ноль — 02. Потеря значимости (underflow) — результат 0 без ошибки, как в TP3: при прерывании FIS ВМ2 не меняет операнды и SP, обработчик пишет 0.0 на место результата и снимает второй операнд (RUNTIME.md §5).
  - **Вывод** (`Write`, `Str`): форматы TP3-dialect §8 с поправкой на точность DEC F: `Write(R)` — 14 символов `  #.######E+##`, `R:n` — не больше 6 цифр после точки. Форматирование написано заново (`FTOA`), цифры получаются точным целочисленным умножением мантиссы на 10^p (RUNTIME.md §5).
- **Сравнения в условиях** (`if`, `while`, `until`) значение не вычисляют, а сразу переходят по условию:
  - `CMP` и `Bxx` с учётом знака: `BLT`, `BGE`;
  - для Byte, Char, указателей и строк — беззнаковые: `BLO`, `BHIS`.
- **Сравнения как значение** дают 0 или 1 в R0.
- **Boolean.** Значение в памяти — байт `0` или `1`, в R0 — слово `0` или `1`.
  - `not` над Boolean-значением — `DEC R0` / `NEG R0` (1 → 0, 0 → 1), а не `COM`: `COM` превратил бы `1` в `177776`. `XOR #1` нельзя: у `XOR` источник только регистр. Над Integer `not` — это `COM` (побитовое отрицание). В условиях `not` не вычисляется, а меняет условие перехода.
  - `and` и `or` над Boolean — `BIC`/`BIS` по значениям 0/1, нормализация не нужна. `and` над R0 и операндом в памяти: операнд дополняется (`COM`) и применяется `BIC`.
  - Boolean-переменная в условии: `TSTB x` / `BEQ` или `BNE`. Истиной считается любое ненулевое значение, так условие корректно и для значений, полученных через `absolute`, `Mem` или `Boolean(5)`. **[?]** Как TP3 обращается с такими значениями в `not` и в сравнениях, проверить на эталоне.
- **[?]** `and`/`or` для Boolean вычисляются полностью, если TP3 так делает (вопрос в TP3-dialect §13).
- Константные подвыражения сворачивает валидатор. В ассемблер попадают только готовые числа с десятичной точкой.

### 7.3. Подпрограммы: кадр и вызов

**Порядок вызова:**
1. Функция, возвращающая Real, — вызывающий резервирует 4 байта под результат: `CMP -(SP), -(SP)`.
2. Функция, возвращающая строку, — вызывающий кладёт адрес временного буфера для результата.
3. Параметры кладутся на стек слева направо.
4. Вложенной подпрограмме (уровень ≥ 2) статическая ссылка передаётся в **R4** (см. ниже).
5. `CALL Pnnnnn`.
6. **Параметры снимает вызываемая подпрограмма.** После возврата на стеке остаётся только Real-результат, если он был. Адрес строкового результата снимается вместе с параметрами.

**Пролог и эпилог:**

```
P00012: MOV     R5, -(SP)       ; сохранить кадр вызывающего
        MOV     SP, R5          ; новый кадр
        MOV     R4, -(SP)       ; статическая ссылка -> -2(R5), только у вложенных
        SUB     #12., SP        ; локальные и временные (если есть)
        ...тело...
        MOV     R5, SP
        MOV     (SP)+, R5
        MOV     (SP), 6(SP)     ; поднять адрес возврата над параметрами (6 байт)
        ADD     #6, SP          ; снять параметры
        RETURN
```

- Если параметров нет, `MOV (SP),N(SP)` и `ADD #N,SP` не нужны. Если `N = 2`, вместо `ADD` можно `TST (SP)+`.
- `N` — размер параметров вместе с адресом строкового результата, но без места под Real-результат: его забирает вызывающий.
- Эпилог не трогает R0–R4, поэтому результат в R0 сохраняется.
- Для подпрограммы без параметров, без локальных переменных и без вложенных обращений к кадру пролог и эпилог можно опустить, оставив `RETURN`. Решает генератор.

**Кадр** (адреса растут вверх):

```
        [место под Real-результат]   ← только у функций Real, 4 байта
        [адрес строкового результата] ← только у функций string
        параметр 1                   ← первый в списке, самый дальний
        ...
        параметр N
 2(R5)  адрес возврата
 0(R5)  R5 вызывающего               ← R5
-2(R5)  статическая ссылка           ← только у вложенных подпрограмм
        локальные переменные
        ...
        временные (строки, множества, конечные значения for, адреса with)
        ← SP
```

Смещения параметров считаются от конца списка: последний параметр лежит в `4(R5)`.

**Передача параметров:**

| Параметр | Что кладётся на стек |
|---|---|
| `var` любого типа, нетипизированный `var` | адрес (1 слово) |
| значение: скаляр, указатель | значение (1 слово, байт расширен нулём) |
| значение: Real | 2 слова |
| значение: строка, множество, массив, запись | адрес; **вызываемая подпрограмма копирует** в свою локальную переменную в прологе |

**Копии структурных параметров-значений.** Валидатор при раскладке кадра выделяет для каждого такого параметра локальную ячейку размера типа (как обычную локальную переменную). В символе параметра хранится смещение копии. Пролог после выделения кадра копирует значение из адреса `n(R5)` в копию (копирование блоков — §7.5). Дальше тело работает только с копией, как с локальной переменной; слово-адрес в `n(R5)` больше не используется. Для строк копируется только `длина+1` байт (шаг 5).

**Результат функции:**
- скаляр, указатель → R0;
- **Real → на стеке**, в месте, которое зарезервировал вызывающий. Внутри функции присваивание имени функции пишет прямо в это место (`n(R5)`), копировать на выходе не нужно. После возврата результат лежит на вершине стека, как любое Real-значение в выражении. Real-значения вообще никогда не возвращаются в регистрах;
- строка → по адресу из скрытого параметра.

Скалярный результат внутри функции — локальная переменная. На выходе она загружается в R0.

**Уровни:**
- Главный блок — уровень 0. Его переменные глобальные, со статическими адресами. R5 главному блоку не нужен.
- Подпрограммы верхнего уровня — уровень 1. Статическая ссылка им не нужна: обращаются к своему кадру и к глобальным переменным.
- Подпрограммы, вложенные в подпрограммы, — уровень 2 и глубже. Получают статическую ссылку на кадр объемлющей подпрограммы.

**Доступ к переменным объемлющих подпрограмм — статическая цепочка.** Ссылка передаётся в R4, а не на стеке (так делает и OMSI Pascal). Тогда она не смешивается с параметрами. Вложенная подпрограмма сохраняет её в `-2(R5)`:

```
; X объявлен на 1 уровень выше, смещение -6
        MOV     -2(R5), R3      ; кадр объемлющей подпрограммы
        MOV     -6(R3), R0
; на 2 уровня выше
        MOV     -2(R5), R3
        MOV     -2(R3), R3
        MOV     -6(R3), R0
```

При вызове подпрограммы уровня `k` из подпрограммы уровня `m` значение R4 вычисляется так:
- `k = m+1` (вызов своей вложенной) — `MOV R5, R4`;
- `k = m` (вызов соседней или рекурсия) — `MOV -2(R5), R4`;
- `k < m` — пройти по цепочке дальше: `MOV -2(R5), R4` / `MOV -2(R4), R4` …

R4 загружается последним, сразу перед `CALL`, после вычисления всех параметров. Вычисление параметров может портить R4.

Статическая цепочка проста и корректна при рекурсии, а платят за неё только вложенные подпрограммы. Дисплей можно рассмотреть позже, если глубокая вложенность окажется частой.

`forward` и `external` используют то же соглашение. `external адрес` вызывается через `CALL @#адрес`.

### 7.4. Операторы

**`if`, `while`, `repeat`** — условные переходы на метки `Lnnnnn`.

**`for`:**

```
; for I := A to B do S       (I локальная)
        MOV     A, R0
        MOV     R0, -2(R5)      ; I := A
        MOV     B, -10.(R5)     ; конечное значение во временную ячейку кадра
        CMP     -2(R5), -10.(R5)
        BGT     L00011          ; цикл не выполняется ни разу
L00010: ...S...
        CMP     -2(R5), -10.(R5)
        BEQ     L00011          ; дошли до конца, I = B
        INC     -2(R5)
        BR      L00010
L00011:
```

- Конечное значение хранится во временной ячейке кадра, а не на стеке, чтобы `goto` из тела цикла не ломал стек.
- Проверка на равенство до `INC` не даёт переменной выйти за границу типа.
- Сравнение знаковое для Integer и беззнаковое для байтовых типов.
- Переменная-байт: `INCB`/`CMPB`.

**`case`:**
- Мало меток — цепочка `CMP` / `BEQ`.
- Плотные метки — таблица переходов: `ASL R0` / `JMP @L00020(R0)` с проверкой границ.
- Порог выбора **[Предложение]**: 6 меток и плотность больше 50%.

**`with`:** адрес записи вычисляется один раз и кладётся во временную ячейку кадра. Поля адресуются через неё: `MOV -12.(R5), R3` / `MOV 4(R3), R0`. Если адрес записи статический (глобальная переменная), поле адресуется напрямую: `V00003+4`.

**`goto`:** `JMP Gnnnnn` в пределах блока. Выйти из блока нельзя, поэтому кадр всегда корректен.

**`Exit`:** переход на эпилог подпрограммы. **`Halt`:** переход на TERM.

### 7.5. Массивы и указатели

- Адрес элемента = база + (индекс − нижняя граница) × размер элемента.
- Константная часть сворачивается в смещение: `V00003-2(R3)`.
- Умножение на степень двойки через `ASL`, иначе `MUL`.
- При `{$R+}` перед вычислением адреса вызывается `RNGCHK` с границами после `CALL` в `.WORD` (ошибка выполнения 90).
- `p^`: адрес в регистре, дальше `(R3)` или `n(R3)`.
- Поле записи — константное смещение: `V00003+4`, `-10.(R5)` с учётом смещения поля, `4(R3)`.
- `Mem[a]` — байт по адресу `a`: адрес в регистр, `CLR R0` / `BISB (R3), R0`. Константный адрес — `@#a`.
- **[P11]** `MemW[a]` — слово по адресу `a` (`array[Integer] of Integer` над всей памятью). Адрес должен быть чётным; не проверяется, нечётный адрес даёт trap по шине, как любое обращение к слову.
- `absolute`: переменная получает адрес другой переменной (тот же операнд) или константный адрес (`@#a`).

**Копирование блоков** (присваивание массивов и записей, копии параметров-значений):
- выравнивание типа «слово» и до 4 слов — отдельные `MOV` (`MOV (R3)+, (R4)+` или со смещениями);
- больше 4 слов — цикл:
  ```
          MOV     #n, R1          ; число слов
  L00012: MOV     (R3)+, (R4)+
          SOB     R1, L00012
  ```
- выравнивание типа «байт» — то же через `MOVB`. Такая структура может лежать по нечётному адресу (массив Char после поля Char), поэтому копировать словами её нельзя;
- адрес источника в R3, назначения в R4 (роли по умолчанию, §7.1). `SOB` есть и на ВМ1.

**Структурные типизированные константы** выводятся в секцию данных по раскладке типа: `.WORD`/`.BYTE` для каждого поля и элемента, `.BLKB` для заполнителей выравнивания, `.EVEN` в конце.

### 7.6. Строки и множества

- Операции со строками — вызовы рантайма с адресами в регистрах:
  - `STCP` — копирование с усечением по максимальной длине;
  - `STCAT` — конкатенация;
  - `STCMP` — сравнение;
  - `COPY`, `POS`, `INSERT`, `DELETE`.
- Максимальная длина получателя передаётся параметром.
- **Временные строки — на стеке.** Промежуточный результат строкового выражения — буфер 256 байт, выделенный `SUB #256., SP`; в R0 его адрес `MOV SP, R0`. Операции пишут результат в буфер на вершине стека, после использования он снимается `ADD #256., SP`. Буферы живут строго по порядку вложенности выражения (как Real на стеке), поэтому их не нужно заранее размещать в кадре, и рекурсия работает без особых мер. Так поступает и TP3.
  - Пример: `S := A + B + C` — копия `A` в буфер, `STCAT` дописывает `B`, затем `C`, `STCP` копирует в `S` с усечением, `ADD #256., SP`.
  - Присваивание без промежуточного результата (`S := T`, `S := 'abc'`) копирует сразу в переменную, без буфера.
  - Буфер всегда 256 байт. **[Позже]** Если максимальная длина результата известна заранее (`Copy` от `string[20]`), буфер можно сделать меньше.
  - Буфер в 256 байт равен запасу `HEAPRS`. При почти полной куче глубоко вложенные строковые выражения могут залезть в кучу без ошибки FF: в прологе столкновение не проверяется (§14).
- **Строковые выражения как аргументы.** Строковый параметр-значение передаётся адресом, вызываемая подпрограмма копирует строку в прологе (§7.3). Переменная или строковая константа передаёт свой адрес сразу. Выражению или Char нужен временный буфер, но буфер между параметрами сломал бы их смещения от R5. Поэтому вызов строится так:
  1. все аргументы, которым нужен буфер, вычисляются заранее, каждый в свой буфер на стеке; буфер результата строковой функции резервируется здесь же;
  2. параметры кладутся слева направо как обычно; адрес буфера — `MOV SP, -(SP)` / `ADD #n, (SP)`, где `n` генератор знает, потому что ведёт глубину стека во время компиляции;
  3. после возврата буферы снимаются одним `ADD #k, SP`.
  ```
  ; P(A + B, 5)
          SUB     #256., SP       ; буфер для A + B
          ...A + B в буфер...
          MOV     SP, -(SP)       ; адрес буфера — первый параметр
          MOV     #5., -(SP)
          CALL    P00003          ; P снимает свои 4 байта параметров
          ADD     #256., SP       ; буфер
  ```
- **Семантика строк, как в TP3:**
  - присваивание обрезает строку по максимальной длине получателя, без ошибки;
  - присваивание строки в Char: ошибка выполнения 10, если длина не 1;
  - сцепление длиннее 255 символов: ошибка 10;
  - `Copy`, `Insert`, `Delete` с позицией вне 1..255: ошибка 11. Позиция за концом строки ошибкой не считается: `Copy` даёт пустую строку, `Delete` ничего не делает, `Insert` дописывает в конец. Результат `Insert` длиннее получателя обрезается без ошибки;
  - сравнение посимвольное беззнаковое, при равном начале короче — меньше;
  - у `var`-параметра строки максимальная длина берётся из формального типа.
- **Множества**: временные буферы по 32 байта на стеке, так же как строки (`SUB #32., SP`, множество в `(SP)`). Операции (`SETUN`, `SETIS`, `SETDF`, `SETEQ`, `SETLE`, `SETIN`) — подпрограммы рантайма.
  - Сжатое хранение разворачивается в 32 байта при загрузке (`SETLD`) и сжимается при записи (`SETST`).
  - `in` с константным множеством — сравнения на месте (до 6 диапазонов) или проверка бита без разворачивания.
  - `in` с переменной-множеством — `SETINV`: бит проверяется прямо в сжатой переменной, без копирования 32 байт. `SETIN` — для множеств-выражений в буфере.
  - Конструктор `[a, b..c]`: константная часть копируется в буфер из 32-байтового образа в данных (или `SETCLR`, если её нет), переменные элементы добавляются `SETADD`/`SETRNG`.
  - **Элементы вне диапазона.** При `{$R+}` элемент конструктора проверяется по диапазону базового типа множества (`RNGSCL`, ошибка 91); при присваивании — по диапазону множества-получателя. Без `{$R+}` элементы вне 0..255 молча отбрасываются. При записи в переменную с более узким диапазоном лишние биты отбрасываются. **[?]** Сверить с эталонным TP3 (TP3-dialect §13).
  - **Присваивание:** множество того же типа — копирование блока; константа — её образ в сжатой раскладке получателя кладётся в данные и копируется блоком; разные раскладки — `SETLD` в буфер, затем `SETST`.
  - **Сравнение:** один и тот же тип — побайтно без разворачивания; иначе оба операнда в буферы и `SETEQ`/`SETLE`. `>=` сводится к `<=` с переставленными операндами.
  - **Параметр-значение.** Вызывающий всегда передаёт адрес развёрнутого 32-байтового буфера: переменная разворачивается `SETLD`, выражение уже в буфере. Буферы готовятся до того, как кладутся параметры, как для строк. Пролог вызываемой подпрограммы сжимает буфер в свою локальную копию через `SETST`. Так у фактического параметра может быть любая совместимая раскладка (`set of 'a'..'z'` в параметр `set of Char`). Это совпадает с TP3: на стеке множество всегда занимает 32 байта, сжатие только при загрузке и записи (руководство TP3, §22.18.3.2.4).

### 7.7. Ввод-вывод

**`Write(a, b:5, r:8:2)`** разворачивается в последовательность вызовов:
1. `WRSETF` — выбрать файл (если не Output);
2. `WRINT` / `WRCH` / `WRSTR` / `WRBOOL` / `WRREAL` с шириной и точностью в регистрах;
3. `WREOL` для `WriteLn`.

У каждой процедуры вывода две точки входа: с шириной поля и без неё (ширина по умолчанию). Ширину по умолчанию не передаём.

**Строковая константа** — самый частый случай в текстовых программах. Она хранится в формате TP3 (байт длины + символы, затем `.EVEN`), а адрес пишется словом сразу после `CALL`:

```
        CALL    WRSTRI          ; Write('Hello')
        .WORD   K00007
...
K00007: .BYTE   5., 'H, 'e, 'l, 'l, 'o
        .EVEN
```

`WRSTRI` берёт адрес строки по адресу возврата и переносит адрес возврата на 2 байта дальше. Вызов занимает 3 слова. Так же можно делать и в других процедурах рантайма с константными аргументами: границы для `RNGCHK` (§7.5), коды ошибок.

Одинаковые строковые константы хранятся один раз.

Аналогично `Read`: `RDINT`, `RDREAL`, `RDCH`, `RDSTR`, `RDLN`.

**Консоль на УКНЦ** — как в vibasc, напрямую через регистры канала 0:
- вывод: `177564` / `177566`;
- ввод: `177560` / `177562`.

**Экран** — управляющие коды текстового терминала УКНЦ (по листингу ПЗУ ПП, ROM3.LST: таблица обработчиков `112462$`):

| TP3 | Код терминала УКНЦ |
|---|---|
| `ClrScr` | `^L` (014): очистка экрана и курсор в начало |
| `GotoXY(X, Y)` | `ESC Y` (Y−1+040) (X−1+040), как у VT52 |
| `ClrEol` | `ESC K` |
| `InsLine`, `DelLine` | нет: терминал умеет вставлять и удалять только символ (`^T`, `^S`), не строку. **[P11]** Пустые процедуры |
| `CrtInit`, `CrtExit` | пустые: настраивать терминал не нужно |
| звук (`Write(^G)`) | `^G`: 0,32 с, 1000 Гц |

`LowVideo`, `NormVideo` не поддерживаются: у УКНЦ нет полуяркости (TP3-dialect, отличия от TP3).

**Проверено в эмуляторе** (до шага 8, программа на ассемблере):
- `^L`, `ESC Y`, `ESC K` работают как описано в ROM3.LST.
- **Опрос `177560`/`177562` при выключенном прерывании от клавиатуры не получает ни одного нажатия.** Через RT-11 (`.TTINR`, EMT 340, прерывание включено) нажатия приходят и копятся в буфере RT-11, даже если программа читает их позже.
- Буквы приходят прописными: `k a` и `k SHIFT+a` дают 101 даже с битом строчных букв JSW (040000). Строчные — через режим строчных букв клавиатуры УКНЦ, в тестах пока не нужны.
- ENTER даёт 015 012, TAB — 011, стрелки — `ESC A`/`ESC D`…, K1 без назначения — ничего. ^C (`k UPR+c`) завершает программу средствами RT-11. Клавиша ЗАБОЙ стирает предыдущий символ уже в буфере RT-11.
- `.GTIM` считает тики 50 Гц: ожидание 150 тиков заняло 150 тиков.

**Ввод с консоли** — через RT-11: INIT больше не выключает прерывание от клавиатуры. Символ — `.TTINR` в специальном режиме терминала (JSW 010000, без ожидания 000100) для `KeyPressed` и `Read(Kbd, C)`; строка для `Read`/`ReadLn` — в обычном (строчном) режиме RT-11: RT-11 сам показывает набираемые символы, выполняет ЗАБОЙ и ^U и отдаёт строку после ENTER. ^C завершает программу средствами RT-11, поэтому `{$C-}` не поддерживается:
- `Read`/`ReadLn` без файла — только режим TP3 по умолчанию `{$B+}`: ввод строки с редактированием (Backspace), не длиннее `BufLen`; правила TP3 при нехватке значений (TP3-dialect §8); ошибка в числе — I/O-ошибка 10. Режим `{$B-}` (чтение из `Input` как из файла) — с файлами, шаг 9.
- `Read` строки с консоли — `.TTYIN` (EMT 340) с ожиданием, до LF; `BufLen` обрезает строку.
- `KeyPressed` — `.TTINR` без ожидания (символ запоминается до следующего чтения); `Read(Kbd, C)` — символ без эха.
- `Eoln` и `Eof` консоли: следующий символ строки ввода — ^Z (конец строки). Клавиши, дающие ESC-последовательность, читаются как ESC и следующие символы.

**`Delay(ms)`** — по таймеру: число тиков сетевого таймера 50 Гц (`.GTIM`), округлённое вверх, шаг 20 мс.

### 7.8. Ошибки выполнения

- Проверку ошибки выполняет вызванная подпрограмма рантайма. Она переходит в `RTERR` с кодом ошибки.
- `RTERR` берёт адрес возврата со стека и печатает:

  ```
  Run-time error 02, PC=001234
  Program aborted
  ```

- Код ошибки печатается в hex, как в TP3. Адрес — восьмеричный адрес **после** команды `CALL`, как в vibasc: по листингу `.LST` место ошибки находится сразу перед ним.
- I/O-ошибки печатаются как `I/O error NN, PC=addr`. При `{$I-}` код ошибки сохраняется для `IOresult` и программа продолжается.

## 9. Оптимизация списка команд и раскладка переходов

Оба прохода работают со списком `CodeLine` каждой подпрограммы в памяти, до записи `.MAC`. У OMSI Pascal то же делает отдельная утилита, которая обрабатывает уже готовый `.MAC`. У нас это часть компилятора.

Порядок проходов:
1. peephole;
2. раскладка переходов.

Раскладка идёт последней: только после всех замен размеры команд окончательные.

### 9.1. Peephole

Набор шаблонов «окно из нескольких команд → замена». Проход повторяется, пока шаблоны срабатывают. Метки — границы окна: если на команду есть переход, через неё шаблон не сработает.

Примеры шаблонов (список пополняется по мере генерации реального кода):

| Было | Стало |
|---|---|
| `Bxx L1` / `BR L2` / `L1:` | `Byy L2` / `L1:` (обратное условие) |
| `BR L1` / `L1:` | `L1:` |
| переход на `BR L2` или `JMP L2` | переход сразу на `L2` |
| `MOV R0, X` / `MOV X, R0` | `MOV R0, X` |
| `MOV R0, -(SP)` / `MOV (SP)+, R0` | (удалить) |
| `MOV #0, dst` | `CLR dst` |
| `ADD #1, dst` / `SUB #1, dst` | `INC dst` / `DEC dst` |
| `CMP dst, #0` | `TST dst` |
| `MOV X, R0` / `ADD R0, Y` (R0 дальше не используется) | `ADD X, Y` |
| `MOV X, R0` / `MOV R0, Y` (R0 дальше не используется) | `MOV X, Y` |
| код после безусловного `BR`/`JMP`/`RETURN` до ближайшей метки | (удалить) |

- Шаблонам с условием «R0 дальше не используется» нужна простая информация о живости регистров. Генератор помечает такие места сам: он знает, когда значение в R0 последний раз использовано.
- Каждый шаблон — отдельная функция в таблице `{шаблон, &Peephole::Method}`, в стиле остального кода.
- Опция `--noopt` выключает peephole для отладки.
- Тесты сравнивают `.MAC` с эталоном, поэтому изменение шаблонов меняет эталоны. Тесты на сам peephole — с `--noopt` и без.

### 9.2. Раскладка переходов

Пределы адресации переходов:
- `Bxx` достигает только −128..+127 слов;
- `SOB` — только 0..63 слова назад.

Pascal-программы легко выходят за эти пределы, а ассемблер не исправляет переходы сам.

Алгоритм:
1. Генератор выдаёт `CodeLine` с размером команды в словах. Размер считается по режимам адресации операндов:
   - `Rn`, `(Rn)`, `(Rn)+`, `-(Rn)` — 0 дополнительных слов;
   - `#n`, `n(Rn)`, метка, `@#n`, `@n(Rn)` — +1 слово на операнд.

   Директивы данных имеют свой размер.
2. Все переходы сначала короткие. Проход по каждой подпрограмме:
   - считаются адреса меток;
   - каждый `Bxx` за пределами диапазона заменяется на обход: `Byy .+6` (обратное условие) + `JMP Lnnnnn`;
   - `BR` вне диапазона заменяется на `JMP`.
3. Проход повторяется, пока есть замены. Размеры только растут, поэтому процесс сходится.
4. `SOB` генерируется только для коротких известных циклов (`FillChar`-подобные в рантайме). В коде пользователя циклы строятся через `DEC` / `BNE`.

Неточная оценка размера опасна: ассемблер выдаст ошибку диапазона. Поэтому в тестах проверяется, что macro11 не выдал ни одного сообщения (как в vibasc).

## 11. Ошибки компиляции

Формат сообщения:

```
PROG.PAS(12,5): error 44: Type mismatch
```

- Номера ошибок из TP3 (TP3-dialect §11.1). Тексты на английском.
- Ошибки стадии выводятся сразу, после стадии — общее количество, как в vibasc.
- После первой синтаксической ошибки в операторе парсер пропускает лексемы до `;` или `end`, чтобы найти и следующие ошибки.
- Для конструкций, которые сознательно не поддерживаются (`overlay`, `Port`, `Bdos`…), — отдельный код, например `error 200: Not supported in Pesto/11`.
- Если кодогенерация для конструкции ещё не написана, генератор выдаёт строку `TODO` в `.MAC` — тест падает, как в vibasc.

## 12. Тесты

**Формат `tests/*.test`.** Заголовок из строк `КЛЮЧ = ЗНАЧЕНИЕ`, затем именованные секции. Секция начинается строкой `=== ИМЯ`; остаток строки после имени не читается, при записи дополняется пробелом и знаками `=` до 71-й позиции. Неизвестный ключ или секция, повтор секции — ошибка теста.

```
OPTIONS = -q
=== SOURCE ============================================================
...исходник TEST.PAS...
=== SOURCE INC.PAS ====================================================
...включаемый файл...
=== OUTPUT ============================================================
...ожидаемый вывод компилятора...
=== MAC EXPECTED ======================================================
...эталонный .MAC...
=== KEYS INPUT ========================================================
...ввод с клавиатуры...
=== SCREEN EXPECTED ===================================================
...ожидаемый вывод программы на экране...
```

- Заголовок: `OPTIONS` — ключи компилятора; `FRAMES` — сколько кадров (50 в секунду) работает программа в эмуляторе, по умолчанию 900.
- `SOURCE` — исходник `TEST.PAS`, обязательна. `SOURCE ИМЯ.ТИП` — дополнительный файл (для `{$I ...}`), таких секций может быть несколько.
- `OUTPUT` — ожидаемый вывод компилятора; нет секции — вывода быть не должно.
- `MAC EXPECTED`, `KEYS INPUT`, `SCREEN EXPECTED` — необязательные. Наличие `SCREEN EXPECTED` включает запуск в эмуляторе.
- `KEYS INPUT` — нажатия клавиш после запуска программы. Символы набираются подряд; перевод строки в секции ничего не значит, это разделитель для удобства. Именованные клавиши — в фигурных скобках: `{ENTER}`, `{ESC}`, `{UP}`, `{K1}` и другие имена команды `k` отладчика; сама фигурная скобка — `{LBRACE}`, `{RBRACE}`. Раннер набирает их после запуска программы с паузой 3 кадра после каждой клавиши: буфер клавиатуры ПП мал, без пауз нажатия теряются. Эхо набранного заранее RT-11 выводит по ходу набора, оно попадает в `SCREEN EXPECTED`.
- После `ClrScr` строки `.RU 1.SAV` на экране нет: тогда вывод программы берётся с начала экрана.

**Конвейер `testrunner`:**
1. Компиляция.
2. Сборка `macro11` (любой вывод ассемблера — ошибка теста).
3. Компоновка `pclink11` (`Undefined globals:` — ошибка теста).
4. Если есть секция `SCREEN EXPECTED`:
   - `rt11dsk` кладёт `.SAV` в копию загрузочного диска RT-11, программа запускается автоматически;
   - **ukncbtl-debugger**: `disk1 attach`, `cfN`, `screentext`;
   - распознанный экран сравнивается с секцией `SCREEN EXPECTED`.

**Самопроверяющиеся тесты** (`05xx-chk-*`): небольшая программа на одну тему, проверки сгруппированы. `Group('ИМЯ')` начинает группу, `Check(Условие, Номер)` считает проверку; по каждой группе печатается строка `ИМЯ PASS n` (при неудачах — `FAIL k:` и номера проваленных проверок), в конце `TOTAL PASS n FAIL m`. Вывод помещается на экран, эталон — весь экран. Ожидаемые значения берутся из семантики TP3, а не из вывода компилятора. Тесты `052x-err-*` проверяют по одной ошибке выполнения.

**Желательные доработки ukncbtl-debugger:**
- запись вывода CPU в канал 0 в файл, вместо распознавания экрана;
- остановка по `.EXIT`;
- команда ввода строки с клавиатуры.

**[Предложение]** Тесты разбиты по этапам плана: лексика, выражения, операторы, подпрограммы, типы, Real, ввод-вывод.

## 14. Открытые вопросы

1. Проверять ли столкновение кучи и стека в прологе подпрограмм, и когда (раздел 6.1). Пока проверка только в `New`/`GetMem`.
2. Как устроен `inline` для PDP-11 (TP3-dialect §10).
3. Ответы эталонного TP3 на вопросы TP3-dialect §13, особенно о полном или сокращённом вычислении `and`/`or`.

Решено:
- статическая цепочка, ссылка передаётся в R4 (§7.3);
- параметры снимает вызываемая подпрограмма (§7.3);
- Real всегда на стеке, результат функции — в месте, которое зарезервировал вызывающий (§7.3);
- `var`-параметры через `@n(R5)`, операции над памятью без R0 (§7.2);
- строковые константы для `Write` — адрес словом после `CALL` (§7.7);
- верх памяти через `.SETTOP`, куча со списком свободных блоков, запас `HEAPRS` = 256 байт (§6.1);
- копирование блоков и копии структурных параметров-значений (§7.3, §7.5);
- `MemW` — расширение Pesto/11 (§7.5);
- временные строки — буферы по 256 байт на стеке; строковые аргументы-выражения вычисляются в буферы до параметров (§7.6);
- множества: буферы по 32 байта, параметр-значение — адрес развёрнутого буфера, `SETINV` для `in` с переменной, правила для элементов вне диапазона (§7.6);
- Real: короткий формат вывода (14 символов), обработчик прерывания FIS, константы с округлением к ближайшему (§7.2);
- экран и клавиатура УКНЦ: коды терминала по ROM3.LST, `Read` в режиме `{$B+}`, `Delay` по таймеру (§7.7);
- файлы: FIB 536 байт, форматы как в TP3, нетипизированные записи по 128 байт, коды I/O-ошибок (§6.4).
